## 1. Description of the data cleaning performed

### 1.1 Overview and comparison with the Phase-I plan

`D` is the City of Chicago Food Inspections extract, `Food-Inspections-20251023.csv`:
**298,869 rows × 17 columns**, one row per inspection, January 2010 – October 2025. Every
missing-value count reported in Phase-I was re-derived from the file at the start of Phase-II and
**all thirteen matched exactly**, so the Phase-I data-quality inventory still describes the data we
cleaned.

The target use case is

> **U1 — identify the most common violation categories associated with failed inspections, broken
> down by facility type and risk level.**

The workflow `W` was designed backwards from U1: each of its steps exists because U1 reads a
particular field, and no step touches a field U1 does not read (except for zero-risk whitespace
normalization).

**Deviations from the Phase-I plan.**

| Phase-I plan | Phase-II actual | Why |
|---|---|---|
| Clean with **OpenRefine**; submit `OpenRefineHistory.json` | Cleaned with **Python 3.9 / pandas 2.3** in a Jupyter notebook; submit `OtherToolHistory.json` generated by an in-notebook operation log | The critical-path step is decomposing the multi-valued `Violations` column into a **second relation** (1 → N), with a per-chunk regex parse and a date-dependent code-book lookup. OpenRefine can split multi-valued cells but cannot emit a second table or apply date-conditional parsing; doing it in code also makes the workflow re-runnable and diff-able. |
| IC checks in unspecified SQL | **DuckDB** SQL executed in-process over the dataframes | Meets the "SQL or Datalog" requirement for `queries.txt` with no database install or ETL, and the *same* SQL text runs against `D` and `D'`, so before/after numbers are strictly comparable. |
| Inner workflow diagram via **OR2YW** | `W2` built by hand from the notebook's numbered step structure (`Workflow.yw` / `Workflow_W2.gv`) | OR2YW consumes an OpenRefine history, which no longer exists. |
| Cleaning owned by Drew (S3) | Cleaning owned by Shray | Re-assigned during Phase-II planning; ownership table above reflects the final split. |
| Violation numbers assumed to be **1–44 ∪ {70}** | Actually **1–45 ∪ {70}** before 2018-07-01 and **1–64** after | Measured from the data — the City replaced its inspection code book in July 2018 (see §1.3, Step 4). |
| Fold city spelling variants, including suburbs | Chicago variants only; suburbs normalized for case/punctuation but never fuzzy-merged | Frequency-based clustering would have merged the correctly spelled `MERRILLVILLE` (1 row) *into* the misspelled `MERRIVILLE` (7 rows). Suburbs are outside U1's scope, so the risk outweighed the benefit. |
| `Risk = 'All'` semantics unresolved | Mapped to `Unknown`, flagged with `risk_is_imputed` | 80 rows (0.03%); `All` is not an ordinal risk level. Recorded as an **assumption**, not a fact. |

### 1.3 Rationale — was each step required for U1?

**Necessary for U1 (U1 is wrong or unanswerable without it):**

* **Step 4 — parse `Violations`.** U1 asks for *violation categories*. In `D` a category is not a
  value anywhere: it is a substring of a free-text cell that also holds up to 39 other violations
  and their inspector narratives. Attempting U1 on `D` with
  `GROUP BY facility_type, risk, violations` returns **54,281 groups for 57,819 failed
  inspections** — 93.9% of failures form their own singleton "category". After the step, U1 is a
  two-line `GROUP BY`.
* **Step 2.5 — parse the date and derive `code_era`.** Chicago replaced its inspection code book on
  **2018-07-01**. The same violation *number* denotes different violations either side of that
  date: `3.` was *"POTENTIALLY HAZARDOUS FOOD MEETS TEMPERATURE REQUIREMENT…"* (9,028 rows) and is
  now *"MANAGEMENT, FOOD EMPLOYEE AND CONDITIONAL EMPLOYEE; KNOWLEDGE…"* (18,124 rows).
  `violation_number → violation_title` is a **violated** functional dependency (45 numbers map to
  two titles); `(code_era, violation_number) → violation_title` **holds**. Grouping U1 by number
  alone would have merged 45 pairs of unrelated categories.
* **Step 3 — `facility_group`.** U1 breaks results down *by facility type*. 520 raw values with a
  one-row long tail (`REST/GROCERY`, `Restuarant`, `GROCERY STORE/ GAS STATION`) is not an analysis
  dimension.
* **Step 2.3 — `Risk`.** U1 breaks results down *by risk level*; the dimension must be a closed
  ordinal domain, and 167 rows were outside it.
* **Step 5 — quality flags.** 3,579 failed inspections have no violation text. Treated naively they
  read as "a failure with zero violations" and deflate every category rate. Flagged and excluded
  explicitly, with the count reported.
* **Step 6 — the 1:N split with referential integrity.** U1 is a join; the join key has to be sound.

**Useful but not required by U1:**

* **Steps 2.1 / 2.2 — City and State.** U1 never groups by city, but it is *stated over Chicago*.
  Cleaning turns "is this really one city's data?" into a single number: 298,450 of 298,869 rows
  (99.86%) are Chicago; 245 rows are genuine suburbs/other states; 174 are unknown.
* **Step 2.5 — `Inspection Type` case folding.** The first follow-up question after U1 is usually
  "were re-inspections worse?"; merging pure case variants (111 → 101) is zero-risk.
* **Step 2.6 — trim-only on names/addresses.** Free normalization. Full entity resolution over
  `DBA Name` was deliberately **not** attempted: it is a project in itself and U1 does not group by
  establishment.

**Deliberately not done, and why:**

* **`Results` was not re-bucketed** (our U0 case): profiling showed a clean 7-value vocabulary, so
  the correct action was to assert it and change nothing — 0 cells changed.
* **No rows were ever deleted** and **no missing value was fabricated.** Out-of-scope and
  problematic rows carry flags instead, so `|D'| = |D|` and every decision is reversible in the
  analysis query rather than baked into the data.

## 3. Workflow model

* **`W1` (outer):** `Workflow_W1.gv` / `.pdf` — S1 acquire & review → S2 profile → **S3 clean
  (= `W2`)** → S4 verify quality (ICs + U1 on `D` and `D'`) → S5 document. Data nodes are the raw
  CSV, the two cleaned relations, and the report artifacts.
* **`W2` (inner):** `Workflow_W2.gv` / `.pdf` — one node per numbered notebook step, showing which
  raw column feeds which rule and where each cleaned column and flag is produced. The dependency
  `inspection_date → code_era → Step 4` is drawn explicitly because it is the non-obvious edge of
  the whole workflow.
* **`Workflow.yw`** carries the YesWorkflow annotations for both; `Workflow.gv` is the combined view.

**Why these tools.** Python/pandas because the critical step is a 1 → N relational decomposition
with conditional parsing; DuckDB because it gives us real SQL over the same in-memory frames, so the
before/after IC queries are textually identical apart from the relation names; the notebook itself as
the operation history because, without OpenRefine, provenance had to be produced by the cleaning code
rather than recovered from a tool's log.

## 4. Conclusions and lessons learned

1. **The hard part was not dirt, it was structure.** The messy-looking fields (city spellings, risk
   blanks) accounted for **1,184 changed cells**; the field that actually blocked U1 was a perfectly
   "clean" text column that packed 974,597 facts into 215,525 cells.
2. **Fixing a data-quality problem can require a domain fact, not a rule.** The 2018 code-book
   change is invisible in the data profile — nothing is null, nothing is malformed — yet ignoring it
   would have silently merged 45 pairs of unrelated violation categories.
3. **Automated cleaning can move data the wrong way.** Frequency-based clustering would have
   "corrected" `MERRILLVILLE` into the misspelling `MERRIVILLE`. Fuzzy merging was therefore
   restricted to the one anchor value U1 depends on.
4. **Flags beat deletion.** Every problematic row is still in `D'` with a boolean explaining why it
   is problematic, so the analysis query — not the pipeline — decides what to exclude, and every
   count in this report is reproducible from `D'` alone.
5. **Not cleaning is a result.** `Results` (U0) needed nothing, and `DBA Name` entity resolution —
   the most visible remaining mess — was skipped because U1 does not read it.
6. **U2 remains unanswerable**, exactly as predicted in Phase-I: `D'` records inspections, never
   health outcomes, and no cleaning can add data the source never collected.

**Next steps / how U1 would ship.** Load both relations into DuckDB, materialize the Step 9 query as
a view, and put a facility-group × risk-level × code-era filter UI on it. The one requirement to
carry forward: any date range spanning 2018-07-01 must group by violation *title*, never by *number*.
The `fail_missing_violations` count belongs on the dashboard as a data-quality footnote.
